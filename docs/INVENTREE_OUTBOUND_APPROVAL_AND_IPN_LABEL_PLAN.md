## 1. 结论先行

本期采用以下固定方案：

1. **出库按每次扫码立即冻结，整张申请单一次性审批和落账。** 每次扫码成功后立刻占住该行数量，页面不等待审批，可以继续扫下一行；点击“提交审批”只改变单据状态，不再重复冻结。
2. **入库按每次扫码记录“待入库”，不增加现存量。** 入库没有现有库存可冻结，因此界面和数据都称“待入库数量”；审批通过后才调用原生 `add_stock()`。
3. **一张申请单允许多条明细，但只允许同一方向、同一来源或目标库位。** 混合入库/出库或跨库位时新建另一张申请单。
4. **审批整单通过或整单失败，不支持部分行审批。** 任一明细在审批时校验失败，整单不落账，出库冻结继续保留，审批人可修复冲突后重试、拒绝，申请人也可撤销。
5. **禁止审批自己的申请。** 仓库管理员也可以发起申请，但必须由另一名有审批权限的用户处理；可以是同组另一位管理员，也可以是配置在更高库位层级的“库存审批主管”，不要求先建设完整组织架构。
6. **申请人可以撤销草稿和待审批申请。** 撤销后立即释放出库冻结；已完成单据不能撤销，只能通过原生库存纠正流程处理。
7. **草稿超时和审批超时分别配置。** 推荐默认值为草稿 30 分钟无活动后失效、提交后 24 小时未审批则失效；超时只释放冻结和通知相关人，绝不自动通过。
8. **新增“商品 IPN 二维码”标签。** 二维码内容是规范化后的纯 `Part.IPN`，可在扫码入库和扫码出库页面直接识别。现有库存项二维码仍是 `INV-SI#`，用于精确识别某条库存项，不能改成 IPN。
9. **本期审批只覆盖扫码直接入库和扫码直接出库。** 销售发货、采购接收、生产领料等原生业务不增加审批节点，但它们必须尊重已冻结数量，不能绕过冻结。

## 2. 现状判断

### 2.1 当前有没有组织架构

当前项目没有“公司—部门—岗位—上下级”的完整业务组织树，但已有足够支撑本期的基础能力：

- Django 用户与用户组；
- InvenTree 角色与库存权限；
- 库位树；
- 库位 Owner（用户或用户组）；
- 通知消息和后台定时任务。

因此本期不新增组织架构模块，而是在库位上配置审批责任人 `approval_owner`。审批责任人仍复用现有 Owner 抽象，可以指向一个用户或一个用户组，并沿库位父级向上继承。

推荐生产配置：

| 角色/组 | 能力 | 能否审批自己的单 |
| --- | --- | --- |
| 仓库操作员 | 扫码、维护草稿、提交、查看和撤销自己的申请 | 否 |
| 仓库管理员 | 操作员全部能力；审批路由到本组的他人申请 | 否 |
| 库存审批主管 | 处理管理员本人申请、异常单或上级库位申请 | 否 |
| 超级管理员 | 配置权限和审批路由；可审批他人的申请 | 否，业务规则不提供绕过 |

审批人解析规则：从申请库位开始向父级遍历，选择最近一个“至少包含一名当前有效、具备审批权限、且不是申请人”的 `approval_owner`。如果当前层配置只有申请人本人，继续向父级寻找；始终找不到则禁止创建可冻结的申请，并返回 `NO_DISTINCT_APPROVER`，避免产生无人能处理的冻结。

### 2.2 当前截图里的二维码是不是 IPN

不是。截图中的二维码内容是 `INV-SI5`，对应 InvenTree 的库存项内部码；页面展示的 IPN 是 `CP-2001`。两者用途必须继续区分：

| 二维码 | 示例 | 代表对象 | 扫码效果 |
| --- | --- | --- | --- |
| 库存项二维码 | `INV-SI5` | 一条确定的 `StockItem`，含库位/批次语义 | 精确选择这条库存项 |
| 物料内部二维码 | `INV-PA#` | 一个 `Part` | 选择该物料 |
| 商品 IPN 二维码（本期新增） | `CP-2001` | 一个 `Part` 的业务商品码 | 按 IPN 进入扫码入/出库申请 |

库存详情原有“查看条码”入口应改文案为“查看库存项二维码”。新增的“商品 IPN 二维码”通过打印标签入口提供，不能覆盖原内部码。

## 3. 业务流程

### 3.1 出库：逐条冻结、整单审批

```text
选择来源库位
      |
      v
创建草稿并解析有效审批人
      |
      v
每次扫码 ----> 锁定库存项 ----> 校验真实可用量 ----> 写 PENDING 明细
      |                                  |
      |                                  +--> 该行数量立即计入冻结
      v
页面继续扫码，不阻塞
      |
      v
提交整单 ------> 通知审批人 ------> 审批人通过
                                      |
                         锁整单和全部库存项（固定顺序）
                                      |
                         整单复验并逐行调用 take_stock()
                                      |
                         Tracking + ScanStockEvent + 单据一起提交
```

选择“逐条扫码立即冻结”而不是“提交整单才冻结”的原因：扫码到提交之间可能持续数分钟；如果不马上占量，多个操作员会同时看到同一份可用库存并形成超领申请。

每次出库扫码事务必须：

1. 校验草稿、方向、来源库位、申请人和审批路由；
2. 解析条码并锁定确定的非序列号 `StockItem`；
3. 以库存层统一可用量重新校验；
4. 创建一条 `outcome=PENDING`、关联申请单的 `ScanStockEvent`；
5. 提交事务后返回最新“现存 / 已分配 / 已冻结 / 可用”数量。

同一个 `client_event_id` 重试只重放原结果，不得再次冻结。扫同一库存项多次时，后端保留每次物理扫码的独立事件用于审计，前端可按库存项聚合显示总数量。

### 3.2 入库：逐条待入库、整单审批

入库扫码不改变 `StockItem.quantity`，只创建待处理明细：

```text
选择目标库位 -> 扫 IPN / INV-PA / INV-SI -> 记录待入库明细
                                             |
                                             v
                                      提交整单审批
                                             |
                                  通过后才 add_stock()
```

规则：

- 已知 Part：在扫码时完成候选选择和上下文收集，但审批前不加库存；审批时在锁内再次确认目标库存项，必要时创建新库存项。
- 未知 IPN：快速建档表单只把规范化建档数据保存到申请明细，审批通过后才在同一事务中创建 Part、创建/选择 StockItem 并入库；拒绝、撤销或超时不会留下半成品 Part。
- 如果等待期间相同 IPN 已被其他流程创建，审批时重新解析；能唯一、兼容地归并则使用现有 Part，否则返回冲突且整单保持待审批。
- 待入库数量不得计入现存量或可用量；在申请单、Part/库位聚合视图中单独显示。

### 3.3 提交、审批、拒绝、撤销与超时

```text
                         +----> CANCELLED
                         |
DRAFT ----> PENDING_APPROVAL ----> APPLYING ----> COMPLETED
  |              |                    |
  |              +----> REJECTED      +-- 事务失败 --> PENDING_APPROVAL
  |              |
  +--------------+----> EXPIRED
```

- `APPLYING` 是审批事务内部状态，不应成为长期可见状态；失败时整个事务回滚到 `PENDING_APPROVAL`。
- 草稿和待审批都允许申请人撤销；待审批撤销要求填写原因。
- 审批拒绝要求填写原因。
- 草稿按最后一次有效写操作的 `activity_at` 计时，页面查询和倒计时不能续期。
- 待审批按 `submitted_at` 计时。
- 超时任务把单据和未处理明细改为终态，出库冻结随状态变化立即释放，并在事务提交后通知申请人和审批人。
- 已拒绝、已撤销、已过期的单据不可恢复；需要重新扫码形成新申请，避免旧明细被静默修改后重新使用。

## 4. 库存数量模型与冻结不变量

### 4.1 展示口径

对出库库存项统一展示：

```text
现存数量 physical_quantity = StockItem.quantity
原生已分配 native_allocated = 生产 + 销售 + 调拨等原生分配
扫码冻结 scan_frozen = 所有 DRAFT / PENDING_APPROVAL 出库明细的 requested_quantity
可用数量 available = max(physical_quantity - native_allocated - scan_frozen, 0)
```

对入库另行展示：

```text
待入库 pending_inbound = DRAFT / PENDING_APPROVAL 入库明细的 requested_quantity
```

`pending_inbound` 不参与 `physical_quantity` 和 `available` 计算。

### 4.2 全局不变量

只在扫码服务里检查冻结是不够的。所有库存变化完成后都必须满足：

```text
StockItem.quantity >= native_allocated + active_scan_frozen
```

实施要求：

- 为 `StockItem` 增加统一的冻结聚合和可用量方法，并让 `unallocated_quantity()` 扣除有效扫码冻结；列表接口使用聚合子查询，禁止逐行 N+1 查询。
- 原生销售/生产/调拨分配使用扣除冻结后的可用量，不能分配被扫码申请占住的部分。
- 原生手工移除、盘点或其他扣量不能把数量降到“原生已分配 + 扫码冻结”以下。
- 存在活动冻结时，禁止删除、合并、拆分、移库或修改会改变库存语义的批次/状态/包装等字段；错误提示应指出占用申请编号。
- 增加数量可以继续执行；纯备注、附件等不影响库存语义的修改可以继续执行。
- 审批事务先锁定请求和全部库存项，再把请求切到事务内 `APPLYING`，使本申请冻结不再重复扣减，然后调用原生 `take_stock()`；任何异常都会回滚状态、数量、Tracking 和事件结果。

本期不把这些原生入口改成审批流程，只保证它们无法破坏扫码冻结。

## 5. 数据模型

### 5.1 新增 `ScanStockApprovalRequest`

建议放在 `stock/models.py`，核心字段如下：

| 字段 | 说明 |
| --- | --- |
| `reference` | 对外申请编号，唯一，例如 `SA-20260827-000123` |
| `direction` | `INBOUND` / `OUTBOUND` |
| `status` | `DRAFT` / `PENDING_APPROVAL` / `APPLYING` / `COMPLETED` / `REJECTED` / `CANCELLED` / `EXPIRED` |
| `location` | 入库目标或出库来源库位；整单唯一 |
| `requester` | 申请人 FK，服务端从 `request.user` 获取 |
| `requester_*_snapshot` | 用户 ID、用户名、显示名快照 |
| `approval_owner` | 创建草稿时解析并固定的审批用户/组 |
| `approval_owner_snapshot` | 名称、类型和路径快照，供长期审计 |
| `submitted_at` | 提交审批时间 |
| `activity_at` | 最后一次有效写操作时间 |
| `expires_at` | 当前阶段的明确失效时间 |
| `decided_by` / `decided_at` | 实际审批人和时间 |
| `decision_note` | 拒绝原因或审批备注 |
| `cancelled_by` / `cancelled_at` / `cancel_note` | 撤销审计 |
| `last_approval_error` | 最近一次审批重试的脱敏业务错误，不改变待审批状态 |
| `created_at` / `updated_at` | 审计时间 |

数据库约束与索引：

- `reference` 唯一；
- `direction`、`status` 使用 `CheckConstraint`；
- 非草稿提交态必须有 `submitted_at`；完成/拒绝必须有决定人和决定时间；
- 审批人不能等于申请人的规则在锁内领域服务强制执行，因为组路由无法只靠简单数据库约束表达；
- 索引至少覆盖 `(status, expires_at)`、`(approval_owner, status, submitted_at)`、`(requester, created_at)` 和 `(location, status)`。

### 5.2 扩展现有 `ScanStockEvent` 作为申请明细

不再新增一份重复的“申请行”流水。每次物理扫码本来就有一个 `ScanStockEvent`，本期增加：

| 字段 | 说明 |
| --- | --- |
| `approval_request` | 可空 FK；历史直接扫码事件保持为空 |
| `request_line_number` | 申请内稳定行号 |
| `requested_part_setup` | 已验证、规范化的未知 IPN 建档快照，仅入库使用 |
| `requested_stock_context` | 目标批次、状态、包装、供应商、有效期和候选选择快照 |
| `terminal_reason` | 被移除、撤销、拒绝、超时等稳定原因码 |

沿用已有字段：`client_event_id`、fingerprint、方向、`PENDING/SUCCESS/FAILED`、请求/实际数量、Part/StockItem/库位关联及快照、操作员快照、前后数量和错误码。

活动明细定义为：申请状态是 `DRAFT` 或 `PENDING_APPROVAL`，事件 `outcome=PENDING`。从草稿移除明细时不物理删除事件，而是改为 `FAILED + REMOVED_FROM_DRAFT`，从活动冻结聚合中退出并保留审计。

增加条件唯一约束：非空申请内的 `request_line_number` 唯一；`client_event_id` 继续全局唯一。历史事件不需要回填申请单。

### 5.3 库位审批配置

在 `StockLocation` 增加可空 `approval_owner`，类型复用现有 Owner：

- 当前库位为空时沿父库位向上找；
- 找到的 Owner 必须能解析出至少一名非申请人且具备审批权限的活动用户；
- 单据创建后保存解析结果快照，不因库位配置改名而篡改历史；
- 审批时仍按当前用户状态、组成员关系和权限复验，已被移出审批组的人不能继续审批。

## 6. 权限、审批路由与通知

新增明确的模型/action 权限，不复用一个过宽的 `stock.change` 代替所有业务授权：

| 动作 | 规则 |
| --- | --- |
| 创建/扫码/提交 | 有扫码申请权限和库位访问权；只能以本人身份发起 |
| 查看 | 申请人看自己的；审批人看路由给自己的；库存审计管理员看全部 |
| 移除草稿行 | 仅草稿申请人 |
| 撤销 | 申请人可撤销自己的草稿/待审批；管理员可应急撤销并必须留原因 |
| 审批/拒绝 | 当前用户属于单据固定审批 Owner、具备审批权限、且不是申请人 |
| 配置审批 Owner/超时 | 库位管理或系统配置管理员 |

建议在部署时创建三个组：`仓库操作员`、`仓库管理员`、`库存审批主管`，但不通过数据迁移自动创建真实用户或强行修改已有组。

通知复用现有 `NotificationMessage`：

- 提交后通知有效审批人；
- 通过、拒绝、撤销、超时后通知申请人；
- 审批冲突不群发，仅把错误展示给本次审批人并记录在单据；
- 所有通知使用 `transaction.on_commit()`，数据库事务回滚时不得发送“已通过”等错误通知；
- 通知包含申请编号、方向、库位、行数、总数量、申请人、截止时间和前端深链接，不在消息里泄露完整原始条码。

## 7. API 与服务层改造

### 7.1 新增申请生命周期 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/stock/scan/requests/` | 创建草稿，固定方向、库位和审批路由 |
| `GET` | `/api/stock/scan/requests/` | 按“我的申请 / 待我审批 / 状态 / 库位 / 方向”过滤 |
| `GET` | `/api/stock/scan/requests/{pk}/` | 单据和明细详情 |
| `DELETE` | `/api/stock/scan/requests/{pk}/lines/{event_pk}/` | 从草稿移除行，逻辑删除并释放冻结 |
| `POST` | `/api/stock/scan/requests/{pk}/submit/` | 提交整单 |
| `POST` | `/api/stock/scan/requests/{pk}/cancel/` | 申请人撤销 |
| `POST` | `/api/stock/scan/requests/{pk}/approve/` | 审批通过并整单落账 |
| `POST` | `/api/stock/scan/requests/{pk}/reject/` | 拒绝整单 |

现有扫码入/出库端点继续负责条码解析和增加明细，但在审批开关启用时必须携带 `approval_request_id`：

- `POST /api/stock/scan/inbound/`
- `POST /api/stock/scan/outbound/`

启用审批后，没有申请 ID 的旧客户端写请求返回 `APPROVAL_REQUEST_REQUIRED`，不能偷偷走原直接扣量路径。关闭功能开关时，当前直接扫码行为保持兼容，便于灰度部署。

所有状态改变都在独立领域服务中实现；View/API 不直接改 `status`、数量或冻结。

### 7.2 扫码冻结事务

出库增加明细的锁顺序固定为：申请单 -> Part（需要时）-> StockItem。可用量必须在锁内重算，成功后才写 PENDING 事件。

入库增加明细只保存已验证的解析结果和建档/库存上下文，不创建库存数量。所有请求 payload 都进入版本化 fingerprint，使用同一 UUID 修改数量、库位、候选或建档资料时返回 409。

### 7.3 整单审批事务

审批通过的事务顺序：

1. `select_for_update()` 锁申请单并确认仍为 `PENDING_APPROVAL`；
2. 验证当前审批人权限、组成员关系和“申请人 != 审批人”；
3. 锁所有活动事件；按 `StockItem.pk` 排序并批量锁定所有已有库存项，避免多单据反向锁导致死锁；
4. 按库存项聚合出库请求量，整单复验可用量、冻结归属、Part/库位/批次/状态和原生分配；入库复验 Part、唯一 IPN 和目标上下文；
5. 把申请切到事务内 `APPLYING`，逐行调用原生 `take_stock()` 或 `add_stock()`；未知入库 Part 也在本事务创建；
6. 为每行写原生 `StockItemTracking`，将对应 `ScanStockEvent` 改为 `SUCCESS` 并写前后快照和实际数量；
7. 把申请改为 `COMPLETED`，保存审批人快照；
8. 事务提交后发送通知和非关键插件事件。

任一行失败则全部回滚，接口返回稳定错误码和冲突行；申请仍为待审批，出库冻结不释放。审批人可以修复外部冲突后重试，也可以拒绝；申请人可以撤销。

### 7.4 超时任务

在 `stock/tasks.py` 使用项目现有计划任务机制，每分钟处理一批超时单据：

- 按 `expires_at` 和主键分页，每批建议 100 条；
- `select_for_update(skip_locked=True)`，避免和提交、审批、撤销互相等待；
- 状态判断和更新必须幂等；并发执行也只能让一张申请过期一次、通知一次；
- 草稿和待审批统一转为 `EXPIRED`，所有 PENDING 事件转终态，出库冻结释放；
- 通知在提交后发送。

## 9. 商品 IPN 二维码标签

### 9.1 标签语义

新增一个可同时注册给 `Part` 和 `StockItem` 的默认标签模板：**商品 IPN 二维码**。

- 二维码 payload：去除首尾空格后的纯 `Part.IPN`，不包装 JSON，不加 `INV-` 前缀；
- 人眼可读内容：商品名称、IPN，必要时显示版本；
- 从 StockItem 打印时仍取 `stock_item.part.IPN`，所以它是商品标签，不代表特定批次或库存项；
- IPN 为空时禁止打印并明确列出问题对象；
- 标签标题或说明标注“按 IPN，非库存项码”，避免和 `INV-SI#` 混淆；
- 建议默认尺寸 50 mm × 30 mm、黑白高对比、保留二维码静区；实际打印机尺寸继续由 InvenTree 标签模板/打印配置控制。

### 9.2 打印入口

复用现有 `PrintingActions.tsx`、标签模板选择、PDF/打印插件和批量选择能力：

- Part 详情和 Part 列表可打印；
- StockItem 详情和库存列表可打印；
- 支持批量选择多个对象；
- 增加打印份数，默认 1，单次限制建议 1–500；
- 本期不新增独立打印服务、不绑定某个品牌打印机，也不增加一个容易混淆的“替换查看条码”按钮。

模板可在 `report/templates/label/` 增加一份源文件，通过 `{% firstof IPN ipn as product_ipn %}` 兼容 Part 与 StockItem 的报表上下文，并在 `report/apps.py` 中分别注册到两个模型。

### 9.3 扫码验收

打印出的标签必须通过扫码枪或相机读出与页面所示完全相同的 IPN，并满足：

- 入库页识别后增加一条待入库明细；
- 出库页识别后按当前来源库位解析候选并立即冻结；
- 同一标签不携带数量、库位、批次或动作，入/出库语义完全由当前页面模式和库位上下文决定；
- IPN 大小写匹配按现有规则处理，但标签打印规范化后的数据库值。

### 13.2 必测用例

后端并发测试使用数据库真实事务和 `TransactionTestCase`，不能用普通 `TestCase` 假装验证行锁：

1. 两个操作员并发冻结同一库存项，成功冻结总量永远不超过可用量；失败方得到 `INSUFFICIENT_AVAILABLE_STOCK`。
2. 相同 `client_event_id` 网络重试不重复冻结；同 UUID 改数量/库位/上下文返回 409。
3. 一个申请包含多条明细，审批任一行失败时所有数量、Tracking 和事件结果都不改变，全部冻结仍保留。
4. 同一申请两名审批人并发点击通过，只能有一个成功落账。
5. 申请人即使属于管理员组或是超级管理员，也不能审批自己的申请；同组另一人和上级审批组可审批。
6. 审批用户提交后被移出审批组，不能继续审批；单据仍可由组中其他有效用户处理。
7. 草稿移除行、撤销、拒绝和超时都只释放一次冻结，不生成成功 Tracking。
8. 超时任务与审批/撤销同时发生时只有一个终态，没有重复通知。
9. 入库待审批期间库存不增加；通过后整单增加；拒绝/撤销/超时不增加。
10. 未知 IPN 申请被拒绝时不创建 Part；通过时 Part、StockItem、数量、Tracking 和事件在同一事务完成。
11. 等待审批期间同 IPN 被创建、目标 StockItem 被删改或来源库存改变时，审批返回明确冲突且不部分落账。
12. 原生分配、手工移除、盘点、移库、拆分、合并和删除不能侵占/破坏活动冻结；增加数量仍可执行。
13. 序列号库存继续返回 `SERIALIZED_STOCK_REQUIRES_ORDER_FLOW`，不能借审批绕过。
14. 功能开关启用后，旧端点不携带申请 ID 无法直接增减库存；关闭时旧行为保持兼容。
15. 库存列表批量查询冻结量不产生 N+1；100 行申请审批的锁定和查询次数有上限断言。
16. Part 和 StockItem 都能生成“商品 IPN 二维码”，解码结果严格等于 IPN；空 IPN 失败；打印标签再扫描可形成入库待处理或出库冻结明细。

### 13.3 前端验收主路径

- 另一审批账号在“待我审批”打开单据并通过，出库现存量才减少或入库现存量才增加；
- 自己的申请不出现可用审批按钮；

- 打印对话框能选择 IPN 商品标签、设置份数并生成可解码输出。

## 14. 失败模式与处理

| 失败模式 | 预防/处理 |
| --- | --- |
| 多人同时扫最后一件 | 锁 StockItem，在锁内按统一可用量创建冻结 |
| 浏览器关闭留下冻结 | 草稿保存在服务端，30 分钟无有效写操作后自动失效 |
| 管理员发起后无人审批 | 创建第一条明细前必须解析到另一名有效审批人，可向父库位审批组升级 |
| 两人同时审批 | 锁申请单，第二人读取终态并返回 409 |
| 审批中一行库存冲突 | 整单事务回滚，保持待审批和冻结，返回冲突行 |
| 原生流程消耗被冻结库存 | 可用量和核心库存修改入口统一扣除/保护冻结 |
| 冻结库存被移库或改批次 | 活动冻结期间阻止会改变库存语义的结构操作 |
| 事务回滚却已发送通知 | 所有通知和非关键任务放到 `on_commit()` |
| 超时任务重复运行 | 批量行锁、状态条件更新、幂等通知 |
| 扫码枪重复提交 | 全局唯一 `client_event_id` + fingerprint 冲突检查 |
| 标签被误认为库存项码 | 模板明确写“商品 IPN”，内部码入口保留并改清楚文案 |
| IPN 为空或重复 | 打印前拒绝空值；沿用忽略大小写唯一和规范化规则 |
| 关闭功能开关后遗留冻结 | 关闭前必须先将活动申请清零；提供检查命令/管理页阻止带活动单据直接关闭 |

## 15. 性能与可运维性

- 单申请默认最多 100 条，审批锁按库存项主键排序，事务内不做打印、发通知或外部网络调用。
- 库存列表通过聚合子查询一次返回冻结量；申请列表使用 `select_related/prefetch_related`，禁止明细 N+1。
- 超时任务分批、可重入，记录处理数量和耗时。
- 增加监控指标：活动冻结总量、最老草稿/待审批时长、审批耗时分布、超时数、审批冲突数、可用量不变量告警、通知失败数。
- 增加只读一致性检查命令，核对活动申请冻结聚合、库存可用量和成功事件/Tracking 关联；不自动修改业务数据。

## 16. 灰度上线与回滚

1. 先发布数据库、后端、前端和标签模板，保持 `SCAN_APPROVAL_ENABLED=False`。
2. 创建/授权操作员、管理员和审批主管组；为试点仓库或父库位配置 `approval_owner`。
3. 运行只读配置检查：每个试点库位是否能为操作员和管理员解析出另一名有效审批人。
4. 在测试库位开启审批，验证出库冻结、入库待处理、撤销、超时和打印标签。
5. 逐仓库启用；启用后监控最老待审批、活动冻结和 409 冲突。
6. 禁止在仍有 `DRAFT/PENDING_APPROVAL` 单据时关闭开关。需要回滚时，先停止新建申请，再由申请人/管理员撤销或完成活动单据，确认冻结为零后关闭开关。

历史已完成的直接扫码事件保持原样，不伪造申请单，不迁移为“已审批”。

## 17. 明确不在本期范围

- 销售发货、采购接收、生产领料、调拨等原生流程增加审批节点；
- 多级串行、会签、加签、转签和抄送工作流；
- 公司部门/岗位/汇报关系组织架构；
- 一张申请跨方向或跨来源/目标库位；
- 部分明细通过、部分数量通过；
- 序列号直接扫码增减；
- FIFO/FEFO 自动选批；
- 指定品牌标签打印机驱动和移动端原生应用；
- 用 IPN 标签替换 InvenTree 内部 `INV-PA#` / `INV-SI#` 二维码。

## 18. 验收标准

本期完成必须同时满足：

1. 出库每扫一条立即冻结，可用量同步下降，页面仍可连续扫码；提交审批前库存现存量不下降。
2. 入库每扫一条只增加待入库量，审批前现存量不增加。
3. 一张申请可包含多条明细，审批通过后所有明细一次成功，或全部不变。
4. 申请人永远不能审批自己的申请；仓库管理员申请可由另一管理员或上级审批主管处理。
5. 草稿和待审批可以撤销；配置的两个超时都能自动终止申请并释放冻结。
6. 其他库存入口无法消耗或破坏活动出库冻结。
7. 原生 `StockItemTracking` 仍是库存事实总账，`ScanStockEvent` 能完整追溯每次物理扫码和审批结果。
8. “商品 IPN 二维码”打印内容严格为 IPN，打印后在入库/出库页可直接扫描；现有库存项二维码仍精确识别 `StockItem`。
9. 并发、幂等、权限、回滚、超时、通知和标签测试全部通过，功能开关关闭时不破坏现有直接扫码。

| 性能 | PASS WITH LIMIT | 默认每单 100 行、稳定锁顺序、批量聚合和分批超时任务 |
| 外部独立评审 | NOT RUN | 实施 PR 完成后再做一次独立代码审查和并发挑战 |

本计划没有待用户决策的阻塞项；默认超时、最大行数和审批组均可在实施/部署时按现场情况调整，不改变核心数据语义。
